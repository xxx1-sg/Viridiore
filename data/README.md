# data/ —— 预测台账

这里存的是**产品和用户之间的对账单**，不是缓存。

```
data/
├── forecast/<YYYY-MM-DD>.json   每天跑一次，写完全部 7 天预测；写完不再修改
├── verified/<YYYY-MM-DD>.json   对某个目标日期的对账结果；一天一份，不可回改
├── ledger.json                  汇总（校准曲线、Brier、明细），给界面读
└── ledger.md                    同一份汇总的人读版，含"模型体检"
```

## 为什么预测和对账分开存

如果把对账结果写回预测文件，就等于允许"先看答案再改题"。分开放，
`forecast/` 里的概率是死数，谁都可以翻回去核对。文件里带 `prev` 字段
（上一份文件的 sha256），改过任一份，链就断。

## 一条记录里有什么

`forecast/*.json` 的每个 entry：

| 字段 | 含义 |
| --- | --- |
| `probability` | 模型当时给的概率（0–100） |
| `baseRate` | 该月基准率，用来区分"模型说话"和"季节说话" |
| `confidence` | 时效折扣后的置信度 |
| `factors` | 每一项加减（含 delta 与理由），概率是可拆的 |
| `inputs` | **输入快照**：云量分层、LCL、云底/云顶、925/850 hPa 温湿、风、降水 |
| `leadDays` | 提前几天说的 |

`inputs` 是全部意义所在。半年后想回答"当时为什么给 62%"，或者模型改版后想重算，
靠的是它，不是那个 62。

## 怎么判定"成立"

规则在 `scripts/forecast/lib.mjs` 的 `JUDGE`，版本号写进每条记录（`ruleVersion`）。

| 模式 | 成立条件 |
| --- | --- |
| 云海 | 低云 ≥ 25% 且 云顶低于山顶 ≥ 50 m 且 观测窗降水 ≤ 0.5 mm |
| 日出 | 降水 ≤ 0.5 mm 且 低云 < 65% 且 云顶不高于山顶 50 m 以上 |
| 星空 | 总云量 < 30% 且 低云 < 25% 且 降水 ≤ 0.2 mm |

观测窗与模型一致：**日出前 90 分钟 — 日出后 30 分钟**（不是日平均，日平均会把关键信息抹平）。

## 三条必须守住的底线

1. **真值只用再分析**（ERA5 归档），不用预报接口的 `past_days`——那是同一套模式自己验自己。
2. **判的是"气象条件成立"，不是"有人看到"**。所以 `basis` 恒为 `reanalysis`；
   用户打卡今后单列 `basis: user`，两套数字分开统计，绝不合并。
3. **逆温这一维没验**。Open-Meteo 的 ERA5 归档不提供 850 / 925 hPa 温度
   （实测全部 `null`，单位字段是 `undefined`），所以记录里标 `degraded: ["inv"]`。
   云量分层、地面温湿、降水、风是可验的——而它们正是云海判据的主体。

## 本地怎么跑

```bash
npm run ledger:collect   # 写今天的预测
npm run ledger:verify    # 对账（ERA5 延迟约 5 天，前几天会一直是 pending）
npm run ledger:report    # 重建 ledger.json / ledger.md
```

CI 在 `.github/workflows/ledger.yml`：每天 21:30 记预测，08:30 对账，自动提交。
